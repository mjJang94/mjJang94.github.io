## 2. 모듈 경계 기준

### 2.1 계층 구조

```
app
 ├── feature/*   (intro, login, home, block, setting, profile, monitoring, schedule)
 ├── core/*      (data, log, phone, permission[+bridge], notification, alarm,
 │                restriction, work, harmful-image, push, firebase)
 ├── ai/*        (nsfw → tflite)
 ├── mobility/*  (location, location-analysis, smombie, location-test)
 ├── domain
 └── common-android → common
```

의존 방향은 `app → feature → core → domain → common-android → common` 단방향이며,
**feature 간 상호 의존이 하나도 없다.** feature 모듈은 모두 리프이고, 화면 간 연결은 app이 조립한다.
순환 의존도 없다.

### 2.2 모듈별 fan-in (참조당하는 횟수)

| 모듈 | fan-in | 성격 |
| --- | --- | --- |
| `common-android` | 21 | Android 공통 유틸 · 디자인 요소 |
| `common` | 19 | 순수 공통(확장 함수, 상수) |
| `domain` | 17 | 모델 · UseCase · Repository 인터페이스 |
| `core:permission` | 6 | 권한 상태 판정 |
| `core:phone` / `core:firebase` / `core:alarm` | 5 | 단말 제어 · 원격 설정 · 스케줄링 |
| `feature:*` | 각 1 (app만) | 화면 단위 |

fan-in 상위 3개가 사실상 전 모듈이 의존하는 축이다. 이 세 모듈의 **공개 API를 바꾸면 전체가 재컴파일**되므로,
빌드 시간 관점에서 가장 민감한 지점이기도 하다(§4.3 참고).

### 2.3 경계 분할 기준

실제 코드에서 읽히는 분할 규칙은 다음 네 가지다.

1. **화면 = feature 모듈** — 라우트 하나가 모듈 하나. 서로를 모른다.
2. **단말 능력 = core 모듈** — 권한, 알람, 알림, 제한, 워커처럼 "OS 기능 한 덩어리"를 단위로 자른다.
3. **도메인 성격이 뚜렷한 영역은 최상위 그룹** — `ai/*`(온디바이스 추론), `mobility/*`(위치·스몸비)는
   core 아래가 아니라 별도 그룹으로 뺐다. `ai:nsfw`가 domain에 전혀 의존하지 않는 자족 모듈인 점이 이 분리의 근거다.
4. **인터페이스 전용 브리지 모듈** — `core:permission:bridge`는 `PermissionBridge.kt` 파일 하나뿐이고
   의존성이 없다. 상위/하위 모듈이 서로를 직접 참조하지 않고 이 모듈만 공유해서 순환을 끊는다.
   `core:permission`, `feature:login`, `app` 3곳이 참조한다.

### 2.4 경계가 흔들리는 지점

측정과 별개로, 지금 구조에서 규칙과 어긋나는 곳은 네 군데다.

- **`domain`이 `common-android`에 의존한다.** domain은 `convention.android.library`로 빌드되는
  Android 라이브러리이고 안드로이드 전용 모듈을 참조한다. Clean Architecture의 도메인 계층 독립성이
  깨져 있고, 순수 Kotlin 모듈이었다면 얻었을 컴파일 속도 이점도 잃는다.
- **`convention.kotlin.library` 플러그인이 사용처 0개다.** 순수 Kotlin 모듈을 상정하고 만들었지만
  적용된 모듈이 없다. 위 항목과 같은 원인 — domain을 JVM 모듈로 만들려던 계획이 멈춘 자리다.
- **`core/mobility`가 고아 모듈이다.** 디렉터리와 소스(`MotionDetector`, entity 다수)가 존재하지만
  `settings.gradle.kts`에 include되어 있지 않아 컴파일되지 않는다. 게다가 build 스크립트가
  `project(":location")`, `project(":location-analysis")` 같은 존재하지 않는 경로를 참조한다.
  include하는 순간 빌드가 깨진다.
- **테스트용 모듈이 프로덕션 그래프에 있다.** `mobility:location-test`(`TestLocationTrackingService` 등)를
  `app`과 `feature:setting`이 `implementation`으로 정식 참조한다. 개발자 메뉴 전용이라면
  디버그 전용 소스셋이나 플레이버 한정 의존으로 격리하는 편이 맞다.

## 3. build-logic 컨벤션 플러그인

### 3.1 구성

```
build-logic/
├── settings.gradle.kts          # 루트의 libs.versions.toml을 그대로 재사용
└── convention/
    ├── build.gradle.kts         # gradlePlugin { } 로 플러그인 5종 id 등록
    └── src/main/java/.../convention/
        ├── AndroidApplicationConventionPlugin.kt   208줄
        ├── AndroidLibraryConventionPlugin.kt        77줄
        ├── AndroidComposeConventionPlugin.kt        35줄
        ├── AndroidHiltConventionPlugin.kt           35줄
        ├── KotlinLibraryConventionPlugin.kt         40줄  (사용처 없음)
        └── common/{Const, AppVersions}.kt           22줄
```

루트 `settings.gradle.kts`에서 `includeBuild("build-logic")`으로 composite build로 물리고,
`build-logic/settings.gradle.kts`가 `../gradle/libs.versions.toml`을 버전 카탈로그로 다시 읽는다.
버전 정의가 한 곳에만 존재한다.

### 3.2 각 플러그인이 흡수한 것

| 플러그인 | 적용 모듈 수 | 흡수한 설정 |
| --- | --- | --- |
| `convention.android.library` | 30 | compileSdk/minSdk, `dev/stage/prod` 플레이버 3종, buildTypes, JDK 17 toolchain·jvmTarget, `-Xlint` 옵션, consumerProguardFiles, `default`·`coroutines`·`lifecycle` 번들 |
| `convention.android.hilt` | 30 | hilt·ksp 플러그인 적용, ksp 인자(`dagger.fastInit` 등), hilt 번들 + 컴파일러 2종 |
| `convention.android.compose` | 12 | compose 컴파일러 플러그인, `buildFeatures.compose`, compose 번들 + lifecycle/hilt-navigation |
| `convention.android.application` | 1 | 위 + 서명 설정 6종(keystore.properties 동적 로드), 3 플레이버 buildConfigField, `nonMinifiedRelease` 빌드 타입, APK/AAB 파일명 규칙 |
| `convention.kotlin.library` | 0 | (미사용) |

특히 값이 큰 건 **플레이버 선언**이다. AGP는 라이브러리 모듈에도 동일한 `flavorDimensions`와
`dev/stage/prod`가 선언되어 있어야 variant matching이 성립한다. 이걸 모듈마다 손으로 적으면
모듈 추가할 때마다 "flavor를 찾을 수 없다"류 실패가 반복된다. 컨벤션 플러그인이 이 선언을
30개 모듈에 자동으로 심는다.

### 3.3 중복 제거량

컨벤션 플러그인이 심는 설정을 각 모듈 DSL로 환산하면 라이브러리 약 45줄, Hilt 약 10줄, Compose 약 8줄이다.

```
인라인 환산: 851(현재 스크립트) + 30×45 + 30×10 + 12×8 ≈ 2,597줄
현재:        851(모듈 스크립트) + 417(build-logic)      = 1,268줄
```

**약 51% 감소**, 그리고 무엇보다 compileSdk·JDK·플레이버 같은 값이 **단일 지점**에 있다.
`Const.kt` 한 줄을 고치면 31개 모듈이 함께 움직인다.

그 결과 모듈 스크립트는 대부분 아래 형태로 수렴한다(평균 27줄, 최소 10줄).

```kotlin
plugins {
    id("convention.android.library")
    id("convention.android.compose")
    id("convention.android.hilt")
}

android {
    namespace = "io.kiwiplus.app.kiwichild.download.feature.home"
    defaultConfig { consumerProguardFiles("consumer-rules.pro") }
}

dependencies {
    implementation(project(":common"))
    implementation(project(":common-android"))
    implementation(project(":domain"))
    implementation(project(":core:phone"))
    implementation(libs.play.services.location)
}
```

### 3.4 아직 남은 중복

- **feature 모듈의 의존성 3종 세트.** 8개 feature 모듈이 전부 `common`, `common-android`, `domain`을
  똑같이 적는다. `convention.feature` 플러그인 하나면 24줄이 사라지고, "feature는 이 셋에만 의존한다"는
  규칙이 코드로 강제된다.
- **`benchmark` 모듈이 컨벤션 밖에 있다.** `com.android.test` 플러그인을 쓰는 유일한 모듈이라
  compileSdk/minSdk/플레이버/JDK 설정 55줄을 전부 직접 들고 있다. 컨벤션이 커버하지 않는 유일한 구멍이고,
  실제로 `compileSdk = 36`으로 `Const.COMPILE_SDK = 37`과 어긋나 있다.
- **`namespace`와 `consumerProguardFiles`.** 30개 모듈이 반복하는데, namespace는 모듈 경로에서
  규칙적으로 파생 가능하고(`io.kiwiplus.app.kiwichild.download` + path), consumerProguardFiles는
  이미 라이브러리 컨벤션 안에 들어 있어 **모듈 쪽 선언이 사실상 중복**이다.

## 4. 빌드 시간

### 4.1 측정값

| 시나리오 | 시간 | 실행된 태스크 |
| --- | --- | --- |
| 설정 단계만 (`help`, warm) | 3.3초 | – |
| 설정 캐시 저장 후 재사용 (`help`) | 2.9초 → **0.76초** | – |
| no-op `:app:assembleDevDebug` | 5.3초 | 1 / 714 |
| domain 주석만 변경 (ABI 무변화) | 8.8초 | **3** / 714 |
| domain에 public 함수 추가 (ABI 변경) | 35.3초 | 62 / 714 |
| 위와 동일 + `--parallel` | **18.1초** | 60 / 714 |

### 4.2 읽히는 것

- **모듈 경계가 실제로 재컴파일을 막는다.** fan-in 17인 `domain`을 고쳐도 주석 수준(ABI 무변화)이면
  714개 태스크 중 **3개만** 실행된다. 모든 모듈 의존이 `api`가 아니라 `implementation`으로 선언돼 있어
  컴파일 회피(compile avoidance)가 정상 동작한다. 예외는 의도적으로 `api`를 쓴
  `common-android → common` 한 곳뿐이다(외부 라이브러리 `api` 노출은 `core:data`의 remote 번들,
  `mobility:location`의 gms-location 2건).
- **병렬 실행 미적용이 가장 큰 손실이다.** ABI 변경 시나리오에서 `--parallel` 하나로 35초 → 18초,
  **48% 단축**됐다. 그런데 `org.gradle.parallel`은 루트 `gradle.properties`에서 주석 처리돼 있고,
  정작 `build-logic/gradle.properties`에만 `parallel`·`caching`·`configureondemand`가 켜져 있다.
  **가벼운 빌드에만 최적화가 걸려 있고, 무거운 본 빌드에는 걸려 있지 않다.**
- **설정 단계는 병목이 아니다.** 31개 모듈에 composite build까지 물려 있음에도 warm 3.3초다.
  컨벤션 플러그인이 `plugins.withId { }`와 lazy API 위주로 작성돼 있고, 모듈 스크립트가 얇은 덕이 크다.

### 4.3 설정 캐시가 막혀 있다

`--configuration-cache`를 켜면 빌드가 실패한다.

```
3 problems were found storing the configuration cache.
- Task `:app:assembleDevDebug` of type `DefaultTask`:
  cannot serialize object of type 'DefaultProject' ...
- ... cannot serialize object of type 'JavaCompile' ...
- ... error writing value of type 'DefaultLegacyConfiguration'
```

원인은 `AndroidApplicationConventionPlugin`의 APK/AAB 파일명 변경 로직이다.

```kotlin
project.tasks.matching { it.name == "assemble$capitalized" }.configureEach {
    doLast {
        if (!project.providers.gradleProperty("distribute").isPresent) return@doLast  // ← 실행 시점에 project 접근
        ...
    }
}
```

`doLast` 블록이 `project`와 `variant`를 그대로 캡처해서 태스크 실행 그래프에 `Project` 참조가 들어간다.
`help` 태스크만으로도 설정 캐시 재사용이 2.9초 → 0.76초(약 74% 단축)로 확인되므로, 이 블록만 정리하면
증분 빌드마다 설정 단계 3초가 통째로 사라진다.

고치는 방향은 단순하다 — `doLast` **바깥에서** 필요한 값(`Provider`, 파일명 문자열, 버전명)을 미리 뽑아
로컬 변수로 캡처하고, 실행 블록 안에서는 `project`에 접근하지 않는다.

## 5. 남은 과제 (우선순위)

| 순위 | 항목 | 근거 |
| --- | --- | --- |
| 1 | 루트 `gradle.properties`에 `org.gradle.parallel=true`, `org.gradle.caching=true` | 측정상 단일 변경으로 48% 단축, 리스크 거의 없음 |
| 2 | 컨벤션 플러그인의 `doLast` project 캡처 제거 → 설정 캐시 활성화 | 증분 빌드마다 설정 3초 제거 |
| 3 | `org.gradle.jvmargs` 상향 (현재 `-Xmx2048m`) | 31개 모듈 + KSP 환경에 2GB는 부족, 4~6GB 권장 |
| 4 | `core/mobility` 고아 모듈 정리 (삭제 또는 경로 수정 후 include) | 컴파일되지 않는 소스가 남아 오해 유발 |
| 5 | `convention.feature` 플러그인 추가 | feature 8개 의존성 중복 제거 + 경계 규칙 강제 |
| 6 | `benchmark` 모듈을 컨벤션에 편입 | compileSdk 36 ↔ Const 37 불일치 해소 |
| 7 | `domain`을 순수 Kotlin 모듈로 (`convention.kotlin.library` 활용) | 계층 독립성 + fan-in 17 모듈의 컴파일 비용 감소 |
| 8 | Hilt `enableAggregatingTask = false` 재검토 | 멀티모듈에서 aggregating task가 증분에 유리한 편 — **미측정, 실측 후 판단 필요** |
| 9 | `mobility:location-test`를 디버그 전용으로 격리 | 테스트 서비스가 릴리스 그래프에 포함됨 |

## 부록: build-logic 도입 시점

`build-logic 구현` 커밋은 2026-01-15로, 당시 저장소에는 `app` 모듈 하나뿐이었다.
즉 **모듈이 늘어난 뒤 중복을 걷어낸 게 아니라, 늘어나기 전에 틀을 먼저 잡은 케이스**다.
따라서 "도입 전후 빌드 스크립트 라인 수" 같은 before/after 실측치는 저장소 이력에 존재하지 않고,
§3.3의 수치는 현재 컨벤션 설정을 각 모듈 DSL로 환산한 추정치다.
