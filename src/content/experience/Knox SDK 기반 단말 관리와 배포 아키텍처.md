> 이 글은 특정 서비스의 구현을 그대로 옮긴 게 아니라, Knox SDK로 자체 단말 관리·배포 체계를 만들 때 마주치는 구조적 판단을 일반화해서 정리한 가이드다.   
실제 라이선스 키, 서버 API 스펙, 내부 화이트/블랙리스트 값 같은 서비스 고유 정보는 담지 않았다.   
다루는 내용은 보호자 동의 하에 자녀 단말을 관리하는 정식 페어런탈 컨트롤 앱의 아키텍처이다.

## 1. 왜 "일반적인 EMM"이 아닌가

Knox 기반 단말 관리라고 하면 보통 Knox Mobile Enrollment(KME)로 기기를 OOB 상태에서 별다른 조작 없이 등록하고, Knox Manage 같은 중앙 EMM 콘솔에서 정책과 앱을 배포하는 그림을 떠올린다.   
기업 BYOD/COPE 환경에는 맞는 그림이지만, **소비자용 서비스 앱**에는 이 전제가 대부분 성립하지 않는다.

- 관리 대상 단말이 회사 자산이 아니라 개인/가정에서 구매한 단말이다.
- 중앙 콘솔에 접속해 정책을 미는 IT 관리자가 없다. "관리자" 역할은 보호자 개인이고, 그 보호자도 단말을 직접 만지지 않는다.
- 기기 등록도 QR/NFC provisioning이 아니라 **삼성전자 총판**에 의해 이뤄진다.

그래서 이런 서비스는 EMM 콘솔을 두는 대신, **앱 자신이 관리 주체(에이전트)가 되는 구조**를 택하게 된다.   
Device Admin 권한과 Knox Enterprise License를 앱 프로세스 안에서 직접 다루고, 정책 배포는 자체 백엔드가 푸시로 트리거한다.

| 구분 | 전통적 EMM (KME + Knox Manage) | 자체 관리형 (이 글의 구조) |
| --- | --- | --- |
| 기기 등록 | 시리얼/IMEI 기반 zero-touch 등록 | 펌웨어 사전탑재 + 앱 내 Device Admin 활성화 유도 |
| 소유자 모델 | Device Owner (완전 위임) | Device Admin + Knox 라이선스 (확장 위임) |
| 정책 제어 주체 | 중앙 EMM 콘솔 | 자체 백엔드 + 클라이언트 내 정책 엔진 |
| 앱 배포 방식 | 콘솔에서 원격 푸시 | 자체 푸시 트리거 → 클라이언트가 다운로드·적용 수행 |
| 대상 | 회사 소유 기기, IT 관리자 존재 | 개인 소유 기기, 비전문 사용자(보호자) |

## 2. 권한 계층: Device Admin → Knox 라이선스 → 확장 정책 API

이 구조에서 "관리 기능이 얼마나 넓은가"는 3단계 권한 체인이 전부 성립하는지에 달려 있다. 하나라도 빠지면 상위 기능은 비활성화된다.

```
1단계  표준 Device Admin
       사용자가 설정 화면에서 명시적으로 동의해야 함
       → 잠금화면 정책, 초기화 방지 등 OS 표준 범위만 제어 가능

2단계  Knox Enterprise License 활성화
       파트너 라이선스 키로 런타임에 활성화
       → 표준 Device Admin으로는 닿지 않는 삼성 확장 정책 그룹의 문이 열림

3단계  Knox 확장 정책 API
       (앱 관리 / 사용 제한 / 보안·위치 정책 등)
       → 표준 스토어 앱 권한 범위를 넘어서는 관리 동작이 여기서부터 가능해짐
```

핵심은 2단계다.   
   
표준 Device Admin API만으로는 앱을 원격으로 설치·삭제하거나 특정 앱 실행을 제한하는 것 같은 동작을 할 수 없다.   
이건 Knox 라이선스가 열어주는 확장 정책 그룹에서만 가능하다.   
그래서 앱은 세션마다 이 체인을 다시 검증해야 한다.   
   
즉 라이선스 상태를 캐싱하지 않고 "지원되는 단말인가 → 관리자 권한이 살아있는가 → 정책이 실제로 적용됐는가" 순서로 매번 확인하는 방어적 설계가 필요했다.   
   
보호자가 설정 화면에서 Device Admin을 임의로 해제하거나, OS 업데이트로 라이선스 활성화가 실패하는 경우가 실제로 발생하기 때문이다.

## 3. 배포 채널 이원화: 스토어 배포 vs 자체 배포

이 권한 체인이 있고 없고의 차이가 가장 크게 드러나는 지점이 **앱 업데이트 방식**이다. 같은 코드베이스를 두 채널로 배포하면, 채널마다 업데이트 메커니즘이 완전히 달라진다.

### 3-1. 스토어 채널

일반적인 Google Play 배포다. 스토어 정책상 앱이 스스로 다른 패키지를 설치하는 동작은 허용되지 않으므로, 업데이트는 전적으로 스토어의 자동 업데이트 기능에 위임한다. 이 채널에서는 자체 배포 로직 자체가 성립하지 않는다.

### 3-2. 자체 배포 채널 (펌웨어 사전탑재)

Knox 확장 API가 열려 있는 채널에서는 스토어를 거치지 않는 자체 배포 파이프라인을 둘 수 있다. 흐름을 일반화하면 이렇다.

```
[백엔드]  신규 버전 배포 트리거 (버전코드, 다운로드 URL)
   │  Push
   ▼
[단말 앱] 현재 버전과 비교 → 업데이트 필요 여부 판단
   │
   ├─ 저장공간 부족            → 실패 사유 보고 후 중단
   ├─ 이미 배포 진행 중         → 중복 요청 무시
   │
   ▼ (조건 통과)
   설치 파일 백그라운드 다운로드
   │
   ▼
   Knox 확장 API로 애플리케이션 정책을 적용해 배포 반영
   (표준 설치 확인 대화상자를 거치지 않고 정책으로 즉시 반영)
   │
   ▼
   결과(성공/실패/사유)를 백엔드에 보고
   │
   ▼
[백엔드]  보호자 화면에서 배포 상태 조회 가능
```

몇 가지 설계 포인트가 있었다.

- **진행 상태를 로컬에 영속화한다.** 다운로드·적용 도중 프로세스가 종료될 수 있어, 진행 중 상태를 남겨두고 재시작 시 이어서 처리하거나 중복 요청을 걸러낸다.
- **실패 사유를 구분해서 보고한다.** "용량 부족"과 "적용 실패"는 서버·보호자 입장에서 대응이 다르다 (전자는 사용자 안내, 후자는 버전 재검토) — 성공/실패를 한 상태값으로 뭉치지 않는다.
- **심사·정책 모드에서는 이 경로 자체를 비활성화한다.** 이런 배포 방식은 스토어 정책상 스토어 채널에서는 허용되지 않으므로, 채널 판별 로직으로 파이프라인 전체를 원천 차단한다.

결과적으로 이 파이프라인은 중앙 EMM 콘솔 없이 "자체 백엔드 + Knox 확장 API" 조합만으로 원격 배포와 적용 상태 추적을 구현한, 축소판 관리형 배포 라인이다.

## 4. Knox 확장 API로 구현 가능한 관리 기능 범주

세부 API 대신 기능 범주로만 정리한다.

| 범주 | 가능한 동작 | 스토어 앱과의 차이 |
| --- | --- | --- |
| 앱 관리 | 원격 설치/삭제, 종료, 표시 아이콘·이름 변경 | 정책 API로 즉시 적용, 대상 앱의 별도 대응 불필요 |
| 사용 제한 | 특정 앱 실행 차단/허용, 화이트리스트 기반 정책 | 대상 앱의 협조 없이 OS 레벨에서 강제 |
| 디바이스 정책 | 잠금화면 문구, 재부팅 스케줄, 무선 인터페이스 제한 | 설정 앱을 거치지 않고 직접 적용 |
| 보안/위치 정책 | 위치 수집 정책, 데이터 보안 정책 강제 | 사용자가 개별 권한 화면에서 임의로 끌 수 없음 |

이 표에 있는 동작들은 모두 정식 페어런탈 컨트롤 계약(단말 최초 설정 시 보호자 동의) 범위 안에서만 활성화된다는 전제가 붙는다. Knox 라이선스가 없으면 이 범주 전체가 사라지고, 앱은 일반 스토어 앱 수준의 권한만 갖는다 — 그래서 앞서 2장에서 다룬 권한 체인 검증이 단순 방어 코드가 아니라, **어떤 기능 세트를 노출할지 자체를 결정하는 분기점**이 된다.

## 5. 운영에서 겪은 제약

- **라이선스 활성화는 100% 보장되지 않는다.** 단말·OS 조합에 따라 활성화가 실패하는 사례가 있어, "지원 단말인가"를 매 세션 런타임에 재확인하는 방어 로직이 필요했다.
- **Device Admin은 사용자가 언제든 해제할 수 있다.** 해제 즉시 관리 기능이 전부 죽으므로, 해제를 감지해 재활성화 화면으로 안내하는 흐름이 필수 기능에 가깝다.
- **같은 계열의 자사 앱끼리 정책이 충돌할 수 있다.** 관리 앱을 여러 개 동시에 설치하면 Knox 정책 그룹을 서로 다른 프로세스가 주장하게 되는데, 이런 충돌은 설치 시점에 상호 배제 규칙으로 미리 걸러내는 편이 사후 디버깅보다 훨씬 싸다.
- **채널 판별이 배포 아키텍처의 전제 조건이다.** 어떤 배포 채널로 실행 중인지 앱이 스스로 정확히 알고 있어야, 자체 배포 경로와 스토어 경로 중 무엇을 열지 안전하게 분기할 수 있다. 이 판별이 틀리면 스토어 채널에서 정책 위반 동작을 시도하는 최악의 시나리오로 이어진다.

## 6. 정리

1. **소비자용 Knox 앱은 "EMM"이 아니라 "자가 관리 에이전트"에 가깝다.** 중앙 콘솔이 없는 대신, 권한 체인(Device Admin → 라이선스 → 확장 API) 검증과 채널 판별을 앱 스스로가 매번 책임진다.
2. **배포 아키텍처는 채널 단위로 완전히 분리해서 설계해야 한다.** 같은 코드베이스라도 "자체 배포가 되는 채널"과 "안 되는 채널"은 업데이트 전략 자체가 다른 시스템이라고 보는 게 맞다.
3. **강력한 권한일수록 상태를 신뢰하지 않고 매번 검증해야 한다.** 라이선스·관리자 권한은 사용자 조작이나 OS 변경으로 언제든 조용히 꺼질 수 있어서, 캐싱된 상태보다 런타임 재확인이 우선이다.
