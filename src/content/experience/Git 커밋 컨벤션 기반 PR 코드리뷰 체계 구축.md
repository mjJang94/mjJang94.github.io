## 1. 배경

기존 개발 프로세스에서 반복적으로 발생하던 문제는 다음과 같았다.

- 커밋 메시지 형식이 개인마다 달라 `git log`만으로 무엇이 바뀌었는지 파악이 어려움
- 릴리즈 시점마다 변경 이력을 수기로 취합 → 누락과 시간 소모 발생
- PR 단위가 비대해 리뷰어가 변경의 **의도**를 파악하지 못한 채 코드만 훑는 리뷰
- QA/기획 측에서 이번 빌드에 뭐가 들어갔는지 물었을 때 답변에 시간이 걸림

핵심 원인은 **커밋 메시지에 구조가 없다는 것**이었다. 구조가 없으면 자동화할 수 없고, 자동화할 수 없으면 사람이 매번 같은 작업을 반복한다. 그래서 커밋 메시지 컨벤션을 먼저 정의하고, 그 위에 PR 코드리뷰와 CHANGELOG 자동화를 얹는 순서로 체계를 만들었다.

## 2. 커밋 메시지 컨벤션

### 2-1. 기본 포맷

```
[prefix] 무엇을 왜 바꿨는지 한 줄 요약- 상세 변경 사항 (선택 사항)- 관련 이슈 번호: #123
```

### 2-2. Prefix 정의

| Prefix | 의미 | 사용 예시 |
| --- | --- | --- |
| `[feat]` | 새 기능 | `[feat] 자녀 위치 히스토리 조회 화면 추가` |
| `[fix]` | 버그 수정 | `[fix] FCM 재수신 시 알림 중복 표시되는 문제 수정` |
| `[refactor]` | 동작 변경 없는 구조 개선 | `[refactor] LocationRepository 인터페이스 분리` |
| `[chore]` | 기타 작업 | `[chore] 사용하지 않는 리소스 정리` |
| `[docs]` | 문서 관련 작업 | `[docs] 모듈 의존성 규칙 README 추가` |
| `[style]` | 포맷/컨벤션 등 스타일 변경 | `[style] ktlint 규칙에 맞춰 import 정렬` |
| `[test]` | 테스트 코드 추가/수정 | `[test] SyncWorker 재시도 로직 테스트 추가` |
| `[perf]` | 성능 개선 | `[perf] 리스트 이미지 디코딩 캐싱으로 스크롤 프레임 드랍 개선` |
| `[ci]` | CI 설정 및 스크립트 변경 | `[ci] CodeBuild 캐시 설정 추가` |
| `[build]` | 빌드 시스템 또는 외부 의존성 변경 | `[build] AGP 8.x 업그레이드` |
| `[revert]` | 커밋 되돌리기 | `[revert] [feat] 위치 히스토리 화면 추가 되돌림` |

> prefix가 없는 커밋은 변경 내용을 기반으로 자동 분류한다. 강제 훅으로 커밋을 막지 않고 fallback을 두는 방식을 선택한 이유는 3-3에 정리했다.
> 

### 2-3. 판단이 애매할 때의 기준

컨벤션 운영에서 실제로 가장 많이 나온 질문은 이건 feat인가 refactor인가였다. 
나는 다음 기준으로 정리했다.

- **사용자가 인지할 수 있는 변화가 있는가** → 있으면 `feat` / `fix`, 없으면 `refactor` / `chore`
- **의도한 동작이 잘못 구현되어 있었는가** → 그렇다면 `fix` (신규 요구사항이면 `feat`)
- **측정 가능한 개선인가** → 벤치마크로 수치를 제시할 수 있으면 `perf`, 아니면 `refactor`
- 두 성격이 섞이면 **커밋을 나눈다**. 나눌 수 없다면 더 큰 영향도를 가진 쪽을 택한다.

## 3. 커밋 → CHANGELOG 자동화

컨벤션의 목적은 형식을 맞추는 것이 아니라 **자동화 가능한 입력값을 만드는 것**이다. 브랜치 단위로 커밋 로그를 파싱해 CHANGELOG를 생성하는 파이프라인을 구성했다.

### 3-1. 처리 흐름

1. **커밋 수집** — 대상 브랜치의 base 기준 diff 및 커밋 로그 수집
2. **분류** — prefix 기준으로 작업 유형 분류, prefix 없는 커밋은 변경 내용 기반 자동 분류
3. **도메인/모듈 식별** — 변경된 파일 경로를 기준으로 어떤 `views`, `widgets`, `features` 모듈이 영향을 받았는지 추출
4. **문서 반영** — `.claude/CHANGELOG.md` 최상단에 신규 블록 추가 (최신 항목이 위)
5. **요약 출력** — 분류별 항목 수와 주요 변경사항을 콘솔에 요약 출력

### 3-2. 생성 포맷

markdown

```markdown
## [브랜치명] — YYYY-MM-DD### 새 기능- 내용 (관련 파일/모듈)### 버그 수정- 내용 (관련 파일/모듈)### 리팩토링- 내용 (관련 파일/모듈)### 기타- 내용**변경 파일**: N개 파일 (추가 A, 수정 M, 삭제 D)**커밋**: N개
```

## 4. PR 기반 코드리뷰에서 얻은 이점

### 4-1. 리뷰 진입 비용 감소

PR 제목과 커밋 prefix만으로 리뷰어가 **어떤 종류의 리뷰를 해야 하는지** 먼저 판단할 수 있다.

- `[refactor]` → 동작 동일성 보장 여부, 테스트 커버리지 중심
- `[feat]` → 요구사항 충족, 엣지 케이스, 상태 관리 설계 중심
- `[perf]` → 벤치마크 근거 제시 여부 중심
- `[build]` / `[ci]` → 빌드 재현성, 캐시 무효화 영향 중심

리뷰어가 **이 PR을 어떤 관점으로 봐야 하는가**를 코드를 열기 전에 정할 수 있다는 점이 가장 큰 변화였다.

### 4-2. 리뷰 단위의 자연스러운 분할

하나의 커밋은 하나의 prefix라는 규칙은 결과적으로 **관심사 분리를 커밋 레벨에서 강제**한다.
기능 추가와 리팩토링이 한 커밋에 섞이지 않으므로, 리뷰어는 diff에서 이건 기능이고 이건 정리구나를 구분하기 위한 시간을 소모하지 않는다.

### 4-3. 릴리즈 노트 작성 비용 제거

브랜치 단위 CHANGELOG가 그대로 릴리즈 노트의 원본이 된다.
QA/기획 측 이번 빌드 변경사항 문의에 문서 링크로 응답 가능해졌고, 배포 전 회귀 테스트 범위를 CHANGELOG의 영향 모듈 목록으로 산정할 수 있게 됐다.

### 4-4. 장애 대응 시 추적성 향상

특정 기능에서 문제가 발생했을 때 `git log --grep="\[fix\]" -- feature/location` 형태로 해당 모듈의 수정 이력만 필터링할 수 있다. 커밋 메시지가 구조화되어 있으면 로그 자체가 검색 가능한 데이터베이스가 된다.

### 4-5. 리뷰 기록의 자산화

PR에 남은 논의는 왜 이 구조를 택했는가에 대한 기록으로 남는다.
예를 들어 상태 관리 패턴 선택이나 의존성 주입 라이브러리 결정 같은 논의는 이후 유사한 설계 판단이 필요할 때 참조 근거가 됐다.

## 5. 단점과 해결 과정

체계를 도입한 뒤 실제로 마주친 문제와 대응이다.

### 5-1. 리뷰 대기로 인한 병목

**문제** — 모든 PR에 리뷰어 승인을 요구하자, 리뷰어가 다른 작업 중일 때 브랜치가 며칠씩 머무는 상황이 발생했다. 특히 오타 수정 수준의 `[docs]`, `[chore]` PR까지 대기하면서 체감 생산성이 떨어졌다.

**해결**

- 변경 유형별로 승인 요건을 차등화했다.
    - `[feat]`, `[fix]`, `[refactor]`, `[perf]` → 리뷰 승인 필수
    - `[docs]`, `[chore]`, `[style]` → CI 통과 시 self-merge 허용
- 리뷰 응답 기준 시간(영업일 기준 24시간)을 합의하고, 초과 시 리뷰어를 재지정하는 규칙을 뒀다.
- 오전 시간대에 리뷰를 먼저 처리하는 습관을 팀 차원에서 정착시켰다. 리뷰를 남는 시간에 하는 일이 아니라 하루의 첫 작업으로 배치한 것이 대기 시간 단축에 가장 효과적이었다.

**실제 사례** — 키위플레이+ Kids, 키위 패밀리 케어, 키위 i, Xplora Teens 등 여러 앱을 병행 유지보수하는 구조라, 리뷰어가 다른 앱 이슈에 물려 있으면 PR이 그대로 대기하는 상황이 반복됐다. 변경 유형별 승인 요건 차등화는 이 구조에서 나온 대응이다.

### 5-2. PR 규모 비대화

**문제** — 기능 하나를 완성해서 올리다 보니 변경 파일이 수십 개인 PR이 생겼다. 이 경우 리뷰어는 사실상 승인 버튼만 누르게 되고, 리뷰가 형식적 절차로 전락한다.

**해결**

- PR 단위를 기능 완성이 아니라 ‘독립적으로 리뷰 가능한 최소 단위’로 재정의했다.
- 큰 기능은 단계별 PR로 분할했다.
    1. 데이터 레이어 (모델, Repository 인터페이스)
    2. 도메인/비즈니스 로직
    3. UI 레이어
    4. 기능 활성화 (feature flag 해제)
- 앞선 PR을 base로 다음 PR을 쌓는 stacked PR 방식으로, 기능 완성 전에도 리뷰를 시작할 수 있게 했다.
- 리팩토링이 필요한 기능 작업은 **`[refactor]` PR을 먼저 분리 병합**한 뒤 `[feat]` PR을 올리는 순서를 규칙화했다. 순수 이동/이름 변경과 실제 로직 변경이 한 diff에 섞이지 않게 하는 것이 목적이다.

**실제 사례** — 기능 하나를 완성해 올린 PR의 변경 파일이 30개에 달한 적이 있다. 리뷰는 승인됐지만, 이후 연관 기능을 작업할 때 리뷰어가 그 PR에서 무엇이 바뀌었는지 인지하지 못한 상태였다. 승인 여부와 무관하게 **리뷰가 실제로는 일어나지 않았다**는 뜻이다. 리뷰의 결과물을 승인 기록이 아니라 팀의 코드 이해도로 봐야 한다는 기준은 이 경험에서 나왔다.

**판단** — 브랜치를 잘게 끊으면 관련 작업이 많을 때 PR 생성 빈도가 눈에 띄게 늘어난다. 그럼에도 이 방식을 택한 이유는 **리뷰의 목적이 승인 절차가 아니라 상호 이해**이기 때문이다. PR 개수를 줄이려고 변경을 한데 묶으면 리뷰는 형식적으로 통과되고, 코드에 대한 이해는 작성자 한 명에게만 남는다. PR을 자주 만드는 부담이 리뷰가 무의미해지는 비용보다 작다고 봤다. 다만 PR 개수 증가는 리뷰 대기 시간을 늘리는 요인이기도 해서, 이 부분은 5-1의 승인 요건 차등화로 흡수했다.

### 5-3. 스타일 논쟁으로 소모되는 리뷰

**문제** — 초기에는 들여쓰기, 네이밍, import 순서 같은 지적이 리뷰 코멘트의 상당 부분을 차지했다. 정작 설계나 로직에 대한 논의는 뒤로 밀렸다.

**해결**

- ktlint / detekt를 CI 필수 게이트로 승격시켜 **스타일은 사람이 아니라 도구가 지적**하도록 했다.
- 포맷 관련 변경은 `[style]` 커밋으로 분리해 로직 diff를 오염시키지 않도록 했다.
- 리뷰 코멘트에 의도 레벨을 명시하는 규칙을 도입했다.
    - `[must]` — 병합 전 반드시 반영
    - `[should]` — 반영 권장, 미반영 시 사유 회신
    - `[nit]` — 취향 수준, 무시 가능
    - `[question]` — 지적이 아닌 이해 목적 질문

`[nit]` 접두사를 명시하는 것만으로 불필요한 왕복이 눈에 띄게 줄었다. 리뷰이가 모든 코멘트를 동등한 무게로 받아들이던 문제가 해소됐기 때문이다.

### 5-4. Prefix 오분류

**문제** — `feat`과 `refactor`, `fix`와 `chore`의 경계가 사람마다 달라 CHANGELOG 분류가 뒤섞였다.

**해결** — 2-3의 판단 기준을 문서화하고, 애매한 경우 커밋을 나누는 원칙을 세웠다. 그럼에도 잘못 분류된 항목은 PR 리뷰 단계에서 확인하고, 병합 시 squash 커밋 메시지에서 최종 교정하도록 했다. 자동 분류의 정확도를 100%로 만들려 하기보다 **교정 지점을 프로세스 안에 명시적으로 배치**하는 쪽이 현실적이었다.

### 5-5. 컨텍스트 없는 PR

**문제** — 코드만 올라온 PR은 리뷰어가 배경을 물어보는 데서 시작해 왕복이 늘었다.

**해결** — PR 템플릿을 도입해 작성자가 최소한의 컨텍스트를 제공하도록 했다.

markdown

```markdown
## 배경왜 이 작업이 필요한가 (관련 이슈 링크)## 변경 사항- [feat] ...- [refactor] ...## 영향 범위변경된 모듈 / 회귀 테스트가 필요한 화면## 검증 방법재현 및 확인 절차 (UI 변경 시 스크린샷 또는 영상)## 리뷰 포인트특히 봐줬으면 하는 부분 / 판단이 갈렸던 지점
```

리뷰 포인트 항목이 특히 효과적이었다.
작성자가 스스로 불확실하다고 느낀 지점을 명시하면 리뷰어의 주의를 그곳에 집중시킬 수 있다.
또한 내가 생각하지 못한 좋은 아이디어를 받아낼 기회도 분명 생겼다.

### 5-6. 커밋 히스토리 오염

**문제** — 리뷰 반영 과정에서 `수정`, `리뷰 반영`, `오타` 같은 무의미한 커밋이 쌓이면 CHANGELOG 자동 생성 품질이 떨어진다.

**해결** — 병합 정책을 squash merge로 통일하고, squash 커밋 메시지를 컨벤션에 맞춰 다시 작성하도록 했다. 작업 브랜치 내부에서는 자유롭게 커밋하되 **메인 브랜치에 남는 히스토리는 컨벤션을 따른다**는 원칙이다. 이로써 개발 중 커밋 부담과 히스토리 품질을 동시에 확보했다.

## 6. 운영 규칙 요약

| 구분 | 규칙 |
| --- | --- |
| 브랜치 | `<prefix>/<이슈번호>-<요약>` (예: `feat/1234-location-history`) |
| 커밋 | `[prefix] 요약` — 하나의 커밋은 하나의 prefix |
| PR 단위 | 독립적으로 리뷰 가능한 최소 단위, 대규모 기능은 stacked PR |
| 승인 | `feat`/`fix`/`refactor`/`perf`는 승인 필수, `docs`/`chore`/`style`은 CI 통과 시 self-merge |
| 리뷰 응답 | 영업일 기준 24시간 내 1차 응답 |
| 코멘트 | `[must]` / `[should]` / `[nit]` / `[question]` 레벨 명시 |
| 병합 | squash merge, 커밋 메시지 컨벤션 준수 |
| 문서 | 병합 시 브랜치 단위 CHANGELOG 자동 생성 |

---

## 7. 정리

이 체계에서 실제로 얻은 교훈은 세 가지다.

1. **규칙은 자동화의 입력값일 때 지켜진다.** 커밋 컨벤션이 CHANGELOG를 만들어내는 재료가 되면서, 규칙 준수의 이유가 정해졌으니까 → 안 지키면 내 작업이 문서에 안 잡힌다로 바뀌었다.
2. **강제보다 회복 경로가 정착률을 높인다.** 커밋 훅으로 막는 대신 자동 분류 fallback과 PR 단계 교정을 두는 쪽이 우회 없이 정착됐다.
3. **리뷰 품질은 리뷰어의 성실성이 아니라 PR 설계에서 결정된다.** PR을 작게 나누고 컨텍스트를 제공하는 것만으로 리뷰 코멘트의 밀도가 달라졌다.
