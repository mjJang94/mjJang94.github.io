## 왜 만들었는가

청첩장을 받으면 가장 먼저 드는 생각이 **저번에 이 사람 결혼식 때 나는 얼마 냈더라**입니다.   
n년 전 계좌 이체 내역 어딘가에 있고, 대부분은 찾지 못한 채 감으로 냅니다.

반대 방향도 마찬가지입니다. 보통 내 결혼식이나 아이 돌잔치가 끝나면 방명록과 봉투가 한 뭉치 남는데, 이를 정리하지 않으면 누구에게 답례해야 하는지, 예전에 내가 냈던 사람 중 누가 오지 않았는지 알 수 없습니다.

기존 가계부 앱은 이 문제를 풀지 못합니다. 가계부는 **월별 지출 합계**를 보는 도구인데 경조사비는 **사람별 누적 차액**이 본질이기 때문입니다.
   
5년 전에 5만 원을 낸 기록이 오늘 얼마를 낼지를 결정하는 종류의 데이터라, 기간으로 잘리는 순간 쓸모가 사라집니다.

그래서 핵심 문제를 세 가지로 잡았습니다.

1. **대조**: 특정 사람과 나 사이에 오간 금액의 차액을 즉시 확인합니다.
2. **정산**: 내 경조사에 누가 얼마를 냈는지, 그리고 **오지 않은 사람이 누구인지** 한 화면에서 확인합니다.
3. **참고**: 다음에 낼 적정 금액을 과거 기록 기반으로 판단합니다.

이 세 가지 외의 모든 것은 부가 기능으로 두었습니다.

## 무엇을 만들었는가

하단 탭 네 개(홈·사람·내 경조사·통계)와 기록 입력 하나로 구성된 단일 Activity 앱입니다. 설정은 홈 상단에서 진입합니다.

- **홈** 올해 나감·받음·차액 요약, 다가오는 내 경조사 D-day, 최근 기록 5건, 기록 추가 FAB
- **사람** 최근순·이름순·차액순 정렬, 관계 칩 필터, 검색, 상세 타임라인, 동명이인 병합
- **기록 입력** 방향 토글, 대형 금액 키패드(`+1만`·`+5만`·`+10만` 퀵 버튼), 사람 선택 시트에서 즉석 등록, 경조사 종류 칩, 선택 항목 접기 영역
- **내 경조사** 등록·수정·삭제, 정산 상세(참석자·총계·평균·최다), **미기록 대조**, 텍스트·CSV 내보내기
- **통계** 연도 선택, 월별 나감·받음 막대 그래프, 종류별·관계별 비중
- **설정** 프리미엄 상태·구매 복원, 백업 파일 내보내기·가져오기(합치기 / 덮어쓰기), 버전 정보
- **실행 취소** 기록 저장·수정·삭제 직후 스낵바에서 되돌리기

차액은 색으로 구분합니다. 내가 더 받았으면 붉은 배지에 `+30,000`, 내가 더 냈으면 파란 배지에 `-50,000`, 같으면 회색 `균형`으로 표시합니다. 숫자를 읽지 않고 색만 봐도 어느 쪽인지 알 수 있어야 한다는 기준으로 잡았습니다.

## 설계에서 고민한 것

### 서버를 두지 않는다

가장 먼저 정하고 끝까지 지킨 제약입니다. Retrofit도 OkHttp도 Firebase도 Ktor도 들어 있지 않습니다. 버전 카탈로그 전체를 뒤져도 HTTP 클라이언트가 없습니다.

예외는 Google Play Billing과 AdMob 두 가지인데, 둘 다 앱이 직접 통신을 구현하는 것이 아니라 스토어·광고 SDK가 자기 서버와 통신하는 구조이며, **사람·기록·경조사 데이터는 그 경로에 실리지 않습니다.**

경조사비 기록은 누가 얼마를 냈는지가 그대로 인간관계의 서열로 읽히는 데이터입니다.   
   
서버에 두면 유출 시 피해가 금액에서 관계로 번질 수 있고, 그 위험을 감수할 만큼 서버가 주는 것이 없었고 동기화도 마찬가지입니다.   
   
이 앱은 1인 1기기로 쓰는 개인 장부라 여러 기기에서 같은 장부를 동시에 수정할 일이 없고, 기기 교체 대비는 파일 백업으로 충분합니다.

### 구독 3종을 1회 결제 하나로 되돌린 것

처음 설계는 월 2,900원 / 연 19,000원 / 평생 29,000원 세 가지에 7일 무료 체험이었습니다. 구현하다가 **5,500원 1회 결제 하나**로 바꿨습니다.

구독은 결제 성공 하나로 끝나지 않습니다. 해지·환불·갱신 실패·유예 기간·재구독이 전부 별개 상태이고, 이를 정확히 반영하려면 결국 Play의 실시간 개발자 알림을 받을 서버가 필요합니다. **서버를 두지 않기로 한 결정이 상품 구성까지 결정한 셈입니다.** 서버 없이 구독을 팔면 상태가 어긋나는 사용자가 반드시 생기고, 그 어긋남은 돈을 냈는데 열리지 않는 경험으로 나타납니다.

바꾸면서 할인 배지, 무료 체험, 기간 표기 관련 코드를 전부 걷어냈습니다. 가격 문자열은 코드에 두지 않고 Play Console 값을 그대로 받아 쓰기 때문에, 나중에 가격을 조정할 때 앱을 다시 올릴 필요가 없습니다.

### 무엇을 잠그지 않을 것인가

수익화 설계에서 가장 오래 붙든 질문입니다.   
   
결론은 **기록 자체는 절대 제한하지 않는다**였습니다. 사람 수, 기록 수, 사용 기간 모두 무제한입니다.

이 앱은 데이터가 쌓여야 가치가 생깁니다. 3년치가 있어야 다음에 얼마를 낼지 판단할 수 있고, 그 3년을 쌓은 사용자만 결제할 이유가 생깁니다. 초반에 인원 수를 막으면 데이터가 쌓이기 전에 이탈하고, 결제는 영원히 일어나지 않습니다.   
   
그래서 유료화는 **쌓인 데이터를 활용하는 부가 기능**에만 걸었습니다. 상세 통계, 정산 내보내기, 적정 금액 제안, 광고 제거가 여기 해당합니다.

로컬 파일 백업과 복원은 무료로 열어 두었습니다. 자기 기록을 꺼내지 못하게 만드는 것은 데이터 마이그레이션을 막는 구조이고, 이 앱에서 가장 해서는 안 되는 일이라고 판단했습니다.

### 화면이 아니라 데이터 계층에서 판단하기

정산 화면의 핵심은 참석자 목록이 아니라 **미기록 대조**입니다. 내가 예전에 냈던 사람 중 이번 내 경조사에 기록이 없는 사람을 찾아내는 기능인데, 이를 리스트 두 개를 순회해 가공하는 방식으로 구현하면 기록이 늘어날수록 느려지고 경계 조건이 코드가 사용처마다 늘어날 수 있어 단일 쿼리로 해결했습니다.

```sql
SELECT p.id, p.name, SUM(r.amount) AS givenAmount
FROM person p
JOIN record r ON r.personId = p.id
    AND r.direction = 'GIVE'
    AND r.eventDate <= (SELECT date FROM my_event WHERE id = :myEventId)
WHERE NOT EXISTS (
    SELECT 1 FROM record x WHERE x.personId = p.id AND x.myEventId = :myEventId
)
GROUP BY p.id
ORDER BY givenAmount DESC
```
기간 집계에서 `eventDate`를 epochDay로 저장하다 보니 SQLite 날짜 함수를 조건절에 쓰면 인덱스로 사용하지 못합니다.   
   
그래서 **경계값은 Kotlin에서 계산해 `BETWEEN`으로 넘기고**, DAO 표면은 `getMonthlySummary(year, month)` 형태를 유지했습니다.

DAO는 도메인 모델 대신 행 DTO(`PersonBalanceRow`, `UnrecordedGuestRow`)를 반환하고 Repository가 매핑합니다.
   
Room이 도메인 타입을 알게 되는 순간 데이터베이스 스펙이 도메인 모델의 모양을 결정하기 시작하기 때문입니다.

### 페이월을 몇 번 띄울 것인가

노출 시점을 네 곳으로 정했습니다. 잠긴 기능을 탭했을 때, 기록 10건 달성 시, 설정 화면 배너, 정산 화면 3회째 진입입니다. 여기서 중요한 것은 **같은 세션에서 두 번 이상 띄우지 않는다**는 제약입니다.

트리거가 여러 개라 조건이 동시에 만족될 수 있어서, 세션 슬롯을 원자적으로 선점하도록 했습니다.

```kotlin
@Singleton
class PaywallSession @Inject constructor() {
    private val claimed = AtomicBoolean(false)
    fun tryClaim(): Boolean = claimed.compareAndSet(false, true)
}
```

1회의 범위는 트리거마다 다릅니다. 기록 10건은 **앱을 지울 때까지 평생 한 번**이라 DataStore에 남기고, 세션 제한은 프로세스가 살아 있는 동안이라 `@Singleton`으로 충분합니다.
   
프로세스가 오래 살아남으면 페이월이 며칠간 다시 뜨지 않을 수 있는데, 과다 노출보다는 이쪽이 낫다고 보고 그대로 두었습니다.
   
정산 방문 횟수는 프리미엄 사용자에게도 계속 셉니다. 세지 않다가 나중에 무료로 돌아오면 횟수가 어긋나기 때문입니다.

### 18개 모듈과 컨벤션 플러그인

```
:app                  진입점, NavHost 조립, DI 최종 결합
:build-logic          컨벤션 플러그인 8종

:core:model           순수 Kotlin 도메인 모델과 enum
:core:common          Result 래퍼, 날짜·통화 유틸, Dispatcher
:core:designsystem    컬러·타이포·셰이프 토큰과 공통 컴포넌트
:core:ui              금액 키패드, 빈 상태, 잠금 오버레이
:core:database        Room Entity, DAO, TypeConverter
:core:datastore       설정과 프리미엄 캐시
:core:data            Repository 구현, 백업·복원
:core:domain          UseCase
:core:billing         Play와 통신하는 유일한 모듈
:core:ads             AdMob 래퍼

:feature:home / person / record / event / stats / settings / paywall
```

`:feature:*` 모듈끼리는 서로 의존하지 않고, 화면 간 이동은 `:app`의 NavHost에서 조립합니다. 처음 명세에는 컨벤션 플러그인이 5종이었는데, feature 모듈 7개가 Compose·Hilt·Navigation·Lifecycle 의존성을 똑같이 반복하고 있어서 `pumasi.android.feature` 플러그인을 추가했습니다.
   
결과적으로 feature 모듈의 빌드 스크립트는 이 정도만 남았습니다.

```kotlin
plugins { alias(libs.plugins.pumasi.android.feature) }
android { namespace = "com.mj.pumasi.feature.person" }
```

**MVI 공통 base 클래스는 만들지 않았습니다.** 화면마다 `State`·`Intent`·`SideEffect`를 직접 정의합니다. 추상화로 줄어드는 코드보다, 문제가 생겼을 때 상위 클래스를 거슬러 올라가며 추적하는 비용이 커 보였습니다. 일회성 이벤트는 `Channel` 기반 SideEffect로, 상태는 `StateFlow`로 통일했습니다.

### 실행 취소를 어디에 둘 것인가

기록을 저장하면 입력 화면은 바로 닫힙니다. 그래서 **그 화면에서는 실행 취소 스낵바를 띄울 수 없습니다.** 스낵바가 뜰 시점이면 스낵바를 소유한 컴포지션이 이미 사라진 뒤입니다.

`RecordUndoBuffer`를 앱 범위 싱글턴으로 두고, 저장·수정·삭제가 여기에 되돌릴 정보를 담으면 앱 스캐폴드가 꺼내 띄우도록 했습니다. 화면 전환을 건너뛰는 상태라 화면 밖에 두는 것이 맞다고 판단했습니다.

### 기기에 올려 보고 나서 고친 것들

에뮬레이터와 프리뷰에서는 멀쩡했던 화면이 실기기에서 무너졌습니다. 한 번에 11건을 고쳤는데, 원인이 겹치는 것들이 있었습니다.

**여백이 두 번 적용되었습니다.** `enableEdgeToEdge` 상태에서 바깥 Scaffold가 inset을 소비하지 않은 채 각 화면의 Scaffold가 같은 inset을 다시 적용하고 있었습니다. 상태바 아래가 두 배로 비었습니다.

**`weight`를 폭 분배로만 이해하고 있었습니다.** 키패드 마지막 줄의 `0` 키가 위 줄과 열이 어긋났는데, weight는 **간격을 뺀 나머지**를 나누기 때문에 칸 수가 다른 줄끼리는 애초에 열이 맞지 않습니다. 세그먼트 컨트롤 인디케이터가 글자 높이만큼만 그려지고 위로 붙은 것도 같은 오해에서 비롯되었습니다. weight는 폭만 정하고 Row의 기본 정렬은 Top입니다.

**실행 취소 스낵바가 사라지지 않았습니다.** `showSnackbar`는 `actionLabel`이 있으면 `duration` 기본값이 `Indefinite`로 바뀝니다. 되돌리기 버튼을 붙인 순간 자동으로 무기한이 된 것인데, 문서를 읽었다면 알 수 있었지만 읽지 않았기 때문에 기기에서 확인하게 되었습니다.

**색 대비가 없어서 눌리는 요소가 눌려 보이지 않았습니다.** surface와 background의 밝기 차이가 2%밖에 되지 않아 카드 경계가 사라졌습니다. 눌리는 요소 전용으로 `surfaceStrong`을 토큰에 추가했습니다.

나머지는 FAB이 마지막 항목을 가리는 문제, 하단 탭과 글자까지 똑같은 상단 제목, 48dp에 못 미치던 터치 타겟이었습니다. **전부 프리뷰에서는 보이지 않는 종류의 결함입니다.** 프리뷰는 컴포저블 하나를 검증하지, 그 컴포저블이 실제 화면에서 다른 것들과 겹쳤을 때를 검증하지 않습니다.

## 배운 것

**하나의 제약이 다른 결정까지 결정합니다.**   
서버를 두지 않기로 한 결정이 영수증 검증 방식을 정했고, 그 다음에는 상품 구성까지 정했습니다. 구독을 팔려면 결국 실시간 알림을 받을 서버가 필요하다는 데까지 가서야 1회 결제로 되돌렸습니다. 제약을 먼저 못 박으면 뒤따르는 선택지가 저절로 줄어듭니다.

**유료화 설계는 무엇을 잠글지가 아니라 무엇을 열어 둘지의 문제였습니다.**   
기록 개수를 막는 쪽이 당장은 전환율이 높아 보이지만, 데이터가 쌓이기 전에 이탈시키면 결제는 영원히 일어나지 않습니다. 로컬 백업을 무료로 둔 것도 같은 판단입니다. 자기 기록을 꺼내지 못하게 만드는 앱은 기능이 아무리 좋아도 신뢰를 얻지 못합니다.

**상태의 출처는 하나여야 합니다.**   
프리미엄 여부를 화면마다 따로 판단하기 시작하면 어느 하나는 반드시 어긋납니다. `PremiumStateRepository`가 내보내는 Flow 하나만 구독하도록 만들고, 시각이 개입하는 판단은 순수 함수로 빼서 테스트로 고정했습니다. 새 화면을 추가해도 판단이 갈라지지 않습니다.

**프리뷰는 컴포저블을 검증하지 화면을 검증하지 않습니다.**   
inset 이중 적용, weight의 열 어긋남, 스낵바가 사라지지 않는 문제는 전부 컴포저블 하나만 봐서는 드러나지 않았습니다. 실기기에 올려 실제로 눌러 보고 나서야 11건이 한꺼번에 나왔습니다.

**명세에서 벗어난 판단은 그 자리에서 적어야 합니다.**   
나중에 코드만 남으면 실수와 판단을 구분할 수 없습니다. 왜 다르게 갔는지를 적어 두는 것까지가 그 작업의 범위였습니다.
